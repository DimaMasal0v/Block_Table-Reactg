1) Зачем использовать generics?
Использование generics в компонентах React делает их более гибкими и переиспользуемыми, так как позволяет определять типы данных, с которыми компонент работает. Это особенно полезно для создания обобщенных компонентов, которые могут принимать различные типы данных в качестве пропсов, сохраняя при этом строгую типизацию.

2) Причина использования уникальных идентификаторов вместо индекса
Использование индексов в качестве ключей в списках React не рекомендуется по нескольким причинам:

Перемещение элементов: Если элементы списка могут быть перемещены, удалены или добавлены, использование индекса как ключа может привести к неправильному отслеживанию состояния компонентов.
Производительность: Использование индексов может заставить React перерендерить все элементы списка при изменении порядка, что ухудшает производительность.
Уникальность: Индексы не гарантируют уникальность элементов, особенно если данные динамически изменяются.

3) Использование индекса в качестве ключа в React не рекомендуется, потому что это может привести к проблемам с производительностью и некорректным поведением компонентов при их обновлении. Ключи помогают React определить, какие элементы были изменены, добавлены или удалены. Когда используется индекс, порядок элементов может измениться, что приведет к неправильной идентификации элементов.

Вместо использования индекса в качестве ключа, можно использовать уникальные идентификаторы из данных, которые гарантируют уникальность ключа для каждого элемента.

1 Этап:

1) FROM node:14 AS build — Используем базовый образ Node.js версии 14 для сборки приложения. Ключевое слово AS build позволяет задать имя этапа сборки, которое будет использоваться на следующем этапе.

2) WORKDIR /app — Устанавливается рабочая директория /app, куда будут копироваться файлы и где будут выполняться команды. Если директория не существует, она создается автоматически.

3) COPY package*.json ./ — Копируются файлы package.json и package-lock.json в рабочую директорию. Эти файлы содержат информацию о зависимостях проекта.

4) RUN npm install — Устанавливаются все зависимости, указанные в package.json. Это включает в себя установку всех пакетов, необходимых для работы вашего приложения.

5) COPY . . — Копируются все файлы из текущей директории (где находится ваш проект) в рабочую директорию контейнера /app. Это включает в себя исходный код приложения и все остальные ресурсы.

6) ARG REACT_APP_TITLE — Определяется аргумент сборки, который может быть передан при создании Docker-образа с помощью команды docker build. Этот аргумент используется для передачи переменных в контейнер на этапе сборки.

7) ENV REACT_APP_TITLE=${REACT_APP_TITLE} — Устанавливается переменная окружения REACT_APP_TITLE на основе значения аргумента сборки. Эта переменная может быть использована внутри React-приложения, например, для динамического изменения заголовка.

8) RUN npm run build — Собирается приложение в режиме продакшн. В результате этого создается оптимизированная версия приложения в директории build. Эти файлы потом будут использоваться для разворачивания приложения.

2 Этап:

1) FROM node:14-slim — Используем легковесный образ Node.js версии 14, чтобы создать финальный образ контейнера. Этот образ занимает меньше места и содержит только минимально необходимые компоненты для работы Node.js.

2) RUN npm install -g serve — Устанавливаем глобально (-g) пакет serve, который используется для обслуживания статических файлов. Этот пакет будет использоваться для запуска вашего React-приложения.

3) WORKDIR /app — Устанавливаем рабочую директорию /app в финальном образе, как и на этапе сборки.

4) COPY --from=build /app/build ./build — Копируем папку build, содержащую оптимизированные файлы приложения, из первого этапа сборки (build) в рабочую директорию финального контейнера.

5) EXPOSE 3000 — Открываем порт 3000 внутри контейнера, чтобы приложение могло принимать внешние подключения на этом порту.

6) CMD ["serve", "-s", "build"] — Определяем команду, которая будет выполнена при запуске контейнера. Команда serve -s build разворачивает собранное React-приложение на сервере и делает его доступным на порту 3000.

Пример запуска контейнера:
docker build --build-arg REACT_APP_TITLE="Соревнования" -t my-react-app .
docker run -p 3000:3000 my-react-app

Зачем использовать pageTitle на уровне компонента, а не на уровне выше?
Передача pageTitle в компонент на уровне ниже позволяет:
1.Инкапсуляция логики компонента: Логика, связанная с тем, как обрабатывать или отображать заголовок, остается внутри компонента. Это делает компонент более самостоятельным и легко переиспользуемым.
2.Повышенная гибкость: Когда заголовок управляется на уровне компонента, это упрощает тестирование и использование компонента в разных контекстах без необходимости изменения родительского компонента.
3.Управление состоянием: Если заголовок зависит от состояния компонента (например, данных из API или других действий), управление заголовком на уровне компонента обеспечивает лучшую управляемость и изоляцию состояния.
Зачем переносить логику на уровень выше?
Перенос логики на уровень выше может потребоваться, если:
1.Управление состоянием или данными: Если заголовок или другие элементы должны управляться централизованно (например, исходя из глобального состояния или маршрутизации).
2.Реиспользование: Если заголовок используется на нескольких страницах или компонентах, лучше управлять им на уровне выше и передавать только те данные, которые необходимы для рендеринга.


1. Что происходит во время npm install?
Когда мы запускаете npm install, происходит следующее:

Чтение package.json и package-lock.json:

npm сначала читает файл package.json, чтобы узнать, какие зависимости определены в секциях dependencies и devDependencies.
Затем, если существует файл package-lock.json, npm читает его, чтобы использовать зафиксированные версии модулей для предотвращения различий в зависимости от версии пакета, которая может быть выбрана в будущем (при установке зависимостей в других средах).
Разрешение зависимостей:

npm проверяет каждую зависимость и начинает разрешать её. Это включает проверку версии пакета, указанной в package.json или package-lock.json, и получение всех её зависимостей (и их зависимостей).
Загрузка пакетов:

Как только зависимости разрешены, npm начинает загрузку всех пакетов из своего реестра (npm registry).
Установка пакетов:

После загрузки пакетов, npm устанавливает их в node_modules директорию.
Создание или обновление package-lock.json:

Если package-lock.json уже существует и все зависимости установлены успешно, файл остается неизменным.
Если package-lock.json отсутствует или есть изменения в установленных версиях зависимостей, npm обновляет или создает новый package-lock.json.
Кеширование:

При установке npm также кеширует загруженные пакеты, чтобы они могли быть повторно использованы в будущем, что ускоряет последующие установки.

2. Проверка и обработка зависимостей
Во время установки npm выполняет несколько проверок и обработок:

Конфликтующие зависимости: Если обнаруживаются конфликтующие версии зависимостей, npm пытается разрешить их автоматически.
Платформозависимые модули: Если какие-либо модули зависят от платформы (например, имеют бинарные зависимости), npm устанавливает их с учетом операционной системы и архитектуры, на которой выполняется установка.
Постинсталляционные скрипты: Некоторые модули могут содержать скрипты, которые запускаются после их установки (например, сборка бинарных модулей). npm запускает эти скрипты в конце процесса установки.
